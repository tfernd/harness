How the replay works

For each session, context per call is uncached input plus cache read plus cache write. Each call adds the new tokens seen in the observed sequence. When the replayed context reaches the threshold T, one compaction call is charged (cache read of the context, output of the summary) and the context restarts from the summary; the next call writes it to the cache. Between compactions a call pays cache read on the existing context, cache write on its new tokens, and the logged output. "actual" is the logged calls plus the modelled cost of the real compactions, so every column contains the same kind of compaction charge. "never" is the same replay with no compaction at all.

What the model leaves out

  • Compaction loses information. Work redone after a compaction (re-reading files, repeated steps) is not priced, so lower thresholds look cheaper than they are.
  • Cache misses from expired cache are kept only as observed: each call keeps the share of its previous context that was not read from cache, applied to the simulated context.
  • The log has no line for the compaction call itself, so its cost is modelled: it reads the context before and writes a summary of the median size as output.
  • Context growth per call is taken from the observed sequence. The jump of a real compaction is replaced by the new tokens of that call; an unmarked context drop uses the logged values of that call.
  • The replay check is close to circular: in the real-compaction mode the growth, cache-miss share and post-compaction size all come from the same log, so a small error shows the bookkeeping is consistent, not that the threshold model predicts anything.
  • Prices are list prices and go stale. On a subscription this shows relative cost, not a bill.
  • Sub-agent runs are replayed with their own contexts and reported apart; their numbers are not added to the main sessions.
  • A replayed session keeps its observed calls; a lower threshold does not change how many calls the work needed.
