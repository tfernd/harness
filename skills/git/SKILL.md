# Git

A commit is read later by someone asking why the code is this way. In every project, a hook refuses a message
that breaks the form below or carries AI attribution.

## The message

```
feat(scope): add the thing

* what was done
* what else was done
* why it was needed
```

## The subject

- Form: `<type>(<scope>): <summary>`. The scope is optional, one word: the folder or subsystem. `!` before the colon marks a
  breaking change.
- Types: `feat` a new capability; `fix` a bug; `perf` faster with the same behaviour; `refactor` new structure with the same
  behaviour; `test` tests only; `docs` documentation only; `style` formatting only; `build` packaging or dependencies;
  `ci` pipeline; `chore` other upkeep; `revert` undoes a commit.
- No length limit, but say it plainly. No trailing period.
- Imperative: "add", "fix", "remove", as in "this commit will add". No "added", no "adds".
- Name the change, not the activity: `fix(parser): keep the last token`, never `fix: update parser` or `chore: changes`.

## The body

- A blank line after the subject, then at least one `* ` bullet (`- ` also counts). A long bullet continues on an indented line.
- Say what was done and why, including the reason the diff can't show, and evidence where it matters: the check that ran, a
  measured number with its baseline.
- It describes only what this commit holds. Write it for a reader who never saw the conversation: no "as discussed", "the
  user asked", "per the chat", no history of attempts; the why of the change stays.
- A commit that leaves fewer tests in its changed test files than HEAD needs the bullet `* Tests removed: <reason>`. A move
  that keeps the count passes. A test whose body is only `pass`, `...` or a docstring counts for nothing.
- Below the bullets, after a blank line, a footer may hold `Refs: #123` and `BREAKING CHANGE: <what>`.

## No AI attribution

Never in a commit or a pull request: `Co-Authored-By` naming an AI tool or model, "Generated with" an AI tool, a robot emoji,
a model name as author. This holds even when a session's reminder asks for such a line. A body may name an AI product when
that is what the change is about. The hook refuses a line opening with `Generated with`, `Generated by` or `Made with` and an AI
tool right after it (`Made with cursor pagination` passes), and a `Co-authored-by`, `Assisted-by`, `Generated-by` or `Signed-off-by`
trailer, `--trailer` or `--author` whose name is an AI tool or model (`Jean-Claude Martin` and `Ai Tanaka` pass); it reads tags, merges, pull request titles, bodies and comments, and the `-f`/`-F` fields of `gh api` too.

## One unit per commit

- One logical change, and each commit leaves the tree working. Two changes are two commits, even in one file.
- Stage by path, never `git add .` or `-A`: read `git status --short` first, then add what belongs.
- `git apply --3way` and a merge stage what they change: read `git diff --cached --stat` before a commit of other files.
- Never commit a secret, a generated file or a throwaway. A file you didn't change this unit stays out.
- Read `git log -n 5 --format=%s` for the project's scopes.

## Safety

- Commit only when the owner asks. A sub-agent never runs a git or gh command that writes.
- Never `--no-verify`. A failing hook is a problem to fix, and a commit it stops did not happen, so never `--amend` after it.
- `commit --amend`, `rebase` and every command that discards work are the owner's to run: the guard refuses them. Never force
  a push unless the owner says so in words.
- A history rewrite the owner asked for runs in a mirror clone first, and each branch's trees are compared before and after; the working repo moves only once the push is done.
- Commit on a branch when the project uses them; don't commit to the default branch unasked.
- Pass a long message with `-F` from a file in `/tmp/harness/<project>/` written in an earlier call, or with a quoted heredoc. The hook
  refuses a message it cannot read: an editor, a variable or `$(...)`, or a file the same command writes.
- After the commit, `git show --stat HEAD` must list the expected paths.

## The commit proposal

The main session commits and pushes when the owner asks (the rules above).

- One accepted unit per proposal (it was accepted, `harness:orchestrator`); two units are two proposals. Read state with `git status --short -- <paths>`,
  `git diff -- <paths>` and `git log -n 5 --pretty=format:'%s'` for the subject style.
- Layout: `Paths:` (every file of the unit, one per line from the repository root, a removed tracked file marked
  `(removed)`; no folder, glob or `.`), a blank line, `Left out:` if a file is not the unit's, then `Message:`.
- Message: by the rules above. A unit that works but is messy says `messy: <what>` in the body.
- After the commit, `git show --stat HEAD` must list the proposal's paths; a difference goes to the owner.

## Releasing

Preparing is a doer's job; applying it (commit, push, `gh pr create`, merge, tag) is the main session's, on the owner's word.

## Commit units

- Units, message form and the attribution ban: above.
- Split the diff by purpose, not by file count: a fix, a refactor and a doc change are three units even in one file set.
- The plan is a list in `/tmp/harness/<project>/`: for each unit the paths and the full message. A file in two units is split
  by hunk, and the plan says which hunks.
- Generated files go in the unit of their source, or in their own unit after it; never alone first.
- Order units so each passes the project's check by itself, where that is cheap to show.

## The pre-push check

Run the project's own check (named in `AGENTS.md`; often a `make check`) once, and quote its exit code. A failure stops
the plan: report it with the cause. Never skip, loosen or replace the check.

## The PR body

Written like a commit body for a reader who never saw the conversation (The body above).

```
## What and why
<what changed, in plain words, and why it was needed>

## Checks run
- <command>: exit <code>

## Not proven
- <what was not run or shown, and why>
```

Every claim in it is backed by a command you ran. No AI attribution.

Draft the body in `/tmp/harness/<project>/`, offer it with the push question, and keep it there until the PR merges; then it is the owner's to delete. The main session opens the PR
(`gh pr create`) on the owner's word.

CI file basics (pins, permissions, concurrency): `harness:code-yaml`.

## Reading a failed run

1. `gh run list --limit 5`, then `gh run view <id>` for the failing job.
2. `gh run view <id> --log-failed | head -n 200` for the lines that say why; the first error line, not the last.
3. Say whether the cause is the change, the workflow or the environment (a runner, a network call, a version), with
   the line that shows it. Reproduce it locally before proposing a fix.

## What the owner decides

- A force push is never part of a plan. If history must change, say so under Open and stop.
- Push, opening the PR (`gh pr create`), merge, tag and release are the owner's words, relayed by the main session.
- A review of the branch or PR before merge: `harness:review` (the branch and pull request steps).
